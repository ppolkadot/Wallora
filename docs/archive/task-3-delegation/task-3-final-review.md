## Remaining blockers

1. **P1, partial original finding 1. A failed cleanup-intent write leaves a rejected account active and restores its private data on reopen.** [Session revocation](C:/Users/A3/Wallora/crates/wallora-core/src/services/session.rs:760) returns early from retirement when the journal insert fails. The [401 fallback](C:/Users/A3/Wallora/crates/wallora-core/src/services/session.rs:775) advances generation and clears memory while retaining the account scope and vault credential. The [app refresh action](C:/Users/A3/Wallora/crates/wallora-app/src/app.rs:156) can still issue keyed work. [Restore](C:/Users/A3/Wallora/crates/wallora-core/src/services/session.rs:381) trusts the unchanged active row and nonempty vault key and loads the old collections before the startup refresh. Before this fix, the 401 path immediately entered Guest and attempted SQLite removal and vault deletion independently.

   Reproduced with file-backed SQLite, an in-memory synthetic vault, and a synthetic upstream-401 payload delivered to the same reducer used by refresh. Sign in with one private collection, then use a raw SQLite connection to install:

   ```sql
   CREATE TRIGGER block_intent BEFORE INSERT ON pending_credential_cleanup
   BEGIN SELECT RAISE(ABORT, 'synthetic intent failure'); END;
   ```

   Apply a current-scope refresh with `Err(ProviderError::Unauthorized)`. Observe the account scope at generation +1, absent in-memory collections, and intact active row, key, and SQLite cache with no intent. Close and reopen SQLite with the same synthetic vault. The old account and private collection are visible before any HTTP request. The regular loopback 401 test exercises only successful intent creation.

   Retire the authenticated scope immediately on 401 and retain cleanup ownership separately. Use an available durable fallback when the intent insert fails. The existing account row can retain the cleanup identifier if the vault key is deleted first on this exceptional path. Cover restart and the case where both stores reject writes. The manual sign-out path already reports the failed persistence attempt and can be retried.

2. **P2, introduced by the fix. Signed-in Settings refresh drops retries and misclassifies a response-body failure.** [Scoped Settings](C:/Users/A3/Wallora/crates/wallora-core/src/provider/client.rs:643) uses the same body-read policy as the [candidate-key probe](C:/Users/A3/Wallora/crates/wallora-core/src/provider/client.rs:703). The [response handler](C:/Users/A3/Wallora/crates/wallora-core/src/provider/client.rs:523) turns a read timeout or interrupted transfer after HTTP 200 into an empty successful response. On signed-in refresh this becomes a Decode error, bypassing the existing transient retry budget.

   Reproduced on literal loopback. Send HTTP 200 and `Content-Length: 3` immediately, send only `{`, and hold the socket open for three seconds. Give an authenticated `Provider::user_settings` request a 500 ms timeout. It returns `Decode { context: "user settings response" }` after one upstream hit. The identical loopback harness linked against a separately built baseline at `9864e8a` returned `Timeout` after three hits. Preserve the exact HTTP 200 requirement for Settings and keep body failures optional only on the candidate-key probe. A signed-in settings refresh needs the usual paced timeout and transport retries.
