# Wallora Task 3 independent review

Reviewed feat/foundation at 9864e8ac705bb0770dc4761fcd97e302c84a58b0 against fd1c181b7787e15128eb5c997e2c3b137f95f330. The brief, implementation report, review package, current code and working-copy decisions were reviewed. The four existing documentation edits are outside the code delta.

**Spec verdict — changes required.** The account/list endpoints, five identity outcomes for decoded fixtures, unkeyed public lookup, opaque account IDs, and Windows vault implementation are present. The normal-path session tests and reported Windows smoke pass do not cover the failures below. Signing in must produce durable SQLite metadata and vault state, and the current logout/switch and proxy paths can violate their guarantees.

**Code quality verdict — changes required.** Session lifetime is split between the Iced busy flags, process-local scope, and SQLite. Vault/SQLite compensations and the proxy rollback lack recoverable ownership or publication boundaries.

## Prioritized findings

1. **P1 — An OS vault entry can outlive all app metadata and cleanup handles.** App boot falls back to in-memory SQLite while keeping real Windows Credential Manager (crates/wallora-app/src/app.rs:34–51). With an unusable database path, sign in using synthetic fixtures and close the app. The UUID row disappears while the vault entry survives. On a healthy DB, killing the process after vault save or after SQLite removal has the same result. A failed rollback delete or a failed logout/revocation vault delete strands the credential as well (crates/wallora-core/src/services/session.rs:480–505, 676–698, 716–755). If both deletes fail, restart can even restore the supposedly signed-out account. Block persistent sign-in when durable SQLite is unavailable. Use a non-secret, durable pending-operation record keyed by AccountId, retain a deactivated/tombstoned account until deletion succeeds, and reconcile interrupted work before restoring sessions. Share the cleanup path between logout and revocation. Test on reopen with a file-backed DB and fake vault at both write boundaries, including DB-open failure, vault-delete failure, and dual cleanup failure. The current partial-failure test explicitly expects the account row to vanish even after vault deletion fails (crates/wallora-core/tests/session.rs:1112–1137).

2. **P1 — A local Windows vault read failure masquerades as upstream 401 and deletes an account.** After a successful restore, make the next vault read return access denied or invalid encoding. The native adapter emits a local error (crates/wallora-windows/src/credentials.rs:47–78). Authorize turns it and missing credentials into Unauthorized before sending HTTP (crates/wallora-core/src/provider/origin.rs:167–201). The normal refresh then calls destructive revocation and claims Wallhaven rejected the key (crates/wallora-core/src/services/session.rs:163–180, 556–560, 676–709). Preserve typed local access/missing/invalid-input errors. Keep transient access failures retryable and reserve revocation for a real 401 from a credentialed upstream request. Test a store that loads successfully on boot, fails one read, then recovers. Assert zero upstream requests on the failed attempt, no vault deletion, preserved metadata, and an accurate notice. Keep a separate actual-401 test.

3. **P1 — A second app instance can repopulate a switched-out account's private cache.** Two launches restore the same active account and each seeds process-local generation 1. Switch Alice to Bob in B, then finish Alice's refresh in A. A accepts its own scope, and the cache upsert checks the foreign key but never checks active state or a durable generation (crates/wallora-app/src/main.rs:78–108, crates/wallora-core/src/services/session.rs:352–368, 542–554, 621–629, crates/wallora-core/src/storage/db.rs:275–309, 386–419). The exact Task 3 schema and SQL reproduced this reinsertion using two shared in-memory SQLite connections. Establish one session owner per DB now or enforce a durable account/generation token in the same transaction as each write and invalidate stale views. An active flag alone misses Alice → Bob → Alice. Add a controlled two-manager test that delays a refresh across switch and switch-back. The later tray/focus-existing-window milestone can remain deferred.

4. **P2 — Session transitions leave the refresh UI stuck or leave superseded tasks running.** Start A's refresh and complete B's sign-in first. Sign-in changes scope but does not retire the old busy flag. A's completion is correctly discarded, so Refresh & verify stays disabled for B (crates/wallora-app/src/app.rs:116–128, 170–205, crates/wallora-app/src/views/account.rs:57–71). A failed switch clears the flag without changing scope, allowing two refreshes in the same generation and letting old results overwrite new ones (app.rs:214–235). Sign-out/switch also discard the pending sign-in ID without aborting keyed work that can continue through the pacer (app.rs:156–172, 207–230). Track refresh ownership by scope and operation, retire or abort tasks on successful transitions, leave current refresh ownership intact on a failed switch, and abort superseded sign-in probes. Exercise real reducer orderings for delayed old success/401, failed switch, and sign-out during probe. The current app test injects a stale 401 after sign-in without starting a prior refresh (app.rs:476–509).

5. **P2 — Proxy Apply publishes uncommitted routing to paced requests.** SessionManager swaps clients before the SQLite write and rebuilds the old mode on save failure (crates/wallora-core/src/services/session.rs:854–870). While the write waits, an API worker takes a clone of the tentative client that rollback cannot take back (crates/wallora-core/src/provider/client.rs:280–290, 403–407, 470–493). Rebuilding also loses the old pools, can reread system proxy configuration, and ignores rollback failure. Build a candidate, persist the normalized setting, then publish via an infallible swap on the same shared client/pacer. Use a blocked then failing preference write and two loopback endpoints to show that no attempt goes via the rejected route. Retain the cooldown test. Existing coverage checks only the eventual mode (crates/wallora-core/tests/session.rs:1179–1192).

6. **P2 — Key validity is coupled to decoding the Settings schema.** A 200 JSON response with a missing or changed per_page gives Decode and exits before identity checking, while an unexpected 2xx with a decodable body can validate a key (crates/wallora-core/src/provider/client.rs:505–517, 677–695, crates/wallora-core/src/domain/account.rs:196–218, crates/wallora-core/src/services/session.rs:111–125). The brief defines 200, 401, and other statuses separately. Carry the exact status classification independently of optional decoded defaults. On confirmed 200 with unreadable defaults, continue identity checks and surface a safe settings fallback. Test malformed-200, unexpected-2xx with valid JSON, and 401 with zero collection requests.

7. **P2 — Refresh can restore a known-stale Verified state after a failed write.** After a former match, make re-verification inconclusive or conflicting and fail the SQLite verification update. Memory downgrades, but cache saving still runs independently. On next boot the account is read as Verified and startup refresh does not reverify (crates/wallora-core/src/services/session.rs:591–635, crates/wallora-app/src/app.rs:101). Commit verification and refreshed cache together, and require fresh verification for a restored value whose durable validity cannot be established before enabling verification-dependent behavior. Test downgrade plus DB fault and reopen. Current item/Favorites authorization impact is deferred to Task 6a, but the Verified label is already affected.

8. **P2 — Browse defaults are displayed and the query seam drops a supported default.** The shell displays preferences, but the only query helper is unused and drops TopRange even though SearchQuery serializes topRange (crates/wallora-app/src/views/search.rs:8–20, crates/wallora-core/src/domain/account.rs:342–350, crates/wallora-core/src/domain/search.rs:206–216, 243–245). Implement and exercise the supported query defaults at the Task 3 seam, including a nondefault range for a Toplist query. Carry per_page through app pagination when that consumer exists. The audited API contract does not list a per_page request parameter, so do not invent one. Task 5 still owns the full discovery and gallery UI.

9. **P2 — Browser hand-off failure has no feedback where the user clicked.** Settings issues OpenUpstreamSettings, ShellExecuteW reports launch failure, and the handler writes an Account-only notice (crates/wallora-app/src/views/settings.rs:107–118, crates/wallora-windows/src/lib.rs:51–66, crates/wallora-app/src/app.rs:271–277, crates/wallora-app/src/views/account.rs:27–45). Render a local Settings error or a shared shell banner, and inject a launcher failure in an app test. A shared banner would also make startup/revocation notices visible from Home and Search.

**P3 cleanup.** The append-only purged_accounts list records even failed purges and has no production consumer (crates/wallora-core/src/services/session.rs:315–317, 370–379, 676–685; crates/wallora-core/tests/session.rs:670). Remove it and assert actual SQLite effects, or return a bounded outcome to the eventual cache integration. The brief also lists docs/privacy.md as cross-cutting and it was absent both before and after Task 3. The new DB and its SQLite sidecars belong in that inventory.
